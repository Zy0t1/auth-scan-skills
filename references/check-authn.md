# A 类检查清单：认证缺陷

> 根因：身份校验机制本身存在缺陷——攻击者无需有效凭据即可冒充身份，或认证协议/流程实现有逻辑漏洞。
> 对应 CVE 簇：认证缺陷 20 条（ArgoCD JWT 伪造 CVSS 10.0、GitLab 密码重置 CVSS 10.0、TeamCity 认证绕过 CVSS 9.8 等）。

## A1. 端点认证覆盖（CWE-306 / 288 / 425）

- [ ] 全局认证策略是"默认拒绝 + 白名单放行"还是"默认放行 + 黑名单保护"？后者逐端点核对黑名单完整性。
- [ ] 管理接口、监控/诊断接口（Actuator、`/metrics`、`/healthz` 详细模式）、插件注册的端点是否被认证过滤器覆盖？
- [ ] 备用通道：CLI 端口、调试端口、RPC 端点是否与 Web 同等认证强度？（Jenkins CLI 反序列化 RCE，CVE-2017-1000353）
- [ ] Webhook 接收器是否有签名校验，还是裸端点？（Spinnaker Gate 无认证创建 pipeline，CVE-2021-43832）
- [ ] 框架自动暴露的端点（Stapler `doXxx`、Actuator、Django admin）是否纳入认证覆盖统计？

## A2. 认证协议实现（CWE-303 / 304 / 347 / 345）

### JWT

- [ ] 签名验证是否在所有配置分支（匿名模式、调试模式、缓存命中、错误恢复）下都不可跳过？（ArgoCD CVE-2022-29165：匿名模式跳过签名验证 → 伪造 admin）
- [ ] `alg` 是否限定白名单？是否存在 `alg=none` 或 RS256→HS256 混淆（用公钥当 HMAC 密钥）？
- [ ] 是否信任 JWT header 中的 `kid`/`jku` 而未做限制（路径穿越/SSRF 选钥）？（CWE-302：信任假定不可变数据）

### OAuth / OIDC

- [ ] 是否逐项校验 `iss`（签发者）、`aud`（必须匹配本服务）、`exp`、`nonce`、签名？
- [ ] 跨服务令牌重用：其他服务的合法令牌能否登录本服务？（ArgoCD 不校验 aud，CVE-2023-22482）
- [ ] claims 校验是"校验关键字段"还是"只检查令牌存在"？（WSO2 OAuth 插件 CVE-2025-47889：任意用户名密码可登录）
- [ ] OAuth 回调地址（redirect_uri）是否严格匹配，能否被篡改到攻击者域名？（CWE-923/939）

### SAML

- [ ] 是否校验 `NotBefore`/`NotOnOrAfter` 时间窗口？
- [ ] 是否维护断言 ID 去重缓存防重放？（Jenkins SAML 插件 CVE-2025-64131：一次截获无限重放）
- [ ] XML 签名校验是否覆盖断言本体（防 XML Signature Wrapping）？

### TLS / 证书

- [ ] 是否存在信任所有证书的分支（`InsecureSkipVerify`、`TrustAllManager`、`verify=False`）？
- [ ] StartTLS 升级后是否仍校验证书链？（Jenkins AD 插件 CVE-2019-1003009：StartTLS 信任所有证书 → MITM 窃取 AD 凭据）
- [ ] 证书过期、吊销（CRL/OCSP）、主机名匹配是否校验？（CWE-295/297/298/299）

### LDAP / 其他

- [ ] 匿名绑定、空密码绑定是否被拒绝？
- [ ] 认证查询的返回结果是否可能多值/注入篡改？

## A3. 认证后身份绑定（CWE-290 / 302 / 807）

认证是一次性的，身份绑定必须是持续的。检查认证通过后，后续操作的身份来源：

- [ ] 服务端是否从**已认证凭据**中提取身份并绑定到会话/连接？还是后续请求信任客户端自报字段？
  - 高危字段：`agent_id`、`node` 名、`team_name`、`commit` 作者、管道所有者、`X-User` 头（Woodpecker gRPC 冒充，CVE-2026-50141；Concourse team_name，CVE-2022-31683）
- [ ] 身份缓存（CLI login 缓存、Token 缓存）是否会被重放冒充？（Jenkins CLI 缓存加密用户名冒充任意用户，CVE-2017-1000354）
- [ ] commit 作者、PR 标题、Webhook payload 中的身份字段是否参与信任决策？（Woodpecker fork 审批绕过，CVE-2026-58370）
- [ ] 以 IP / Referer / rDNS 作为认证依据？（CWE-291/293/350）

## A4. 认证流程缺陷（CWE-640 场景 → 落点 620 / 287 / 304）

### 密码重置 / 账户恢复

- [ ] 重置链接是否绑定用户 ID + 一次性 Token + 短时效？
- [ ] 邮箱参数是否严格校验归属？是否拒绝数组/多值参数注入（`email=victim&email=attacker`）？（GitLab CVE-2023-7028，CVSS 10.0：重置邮件同时发给攻击者）
- [ ] 修改密码/邮箱时是否验证原密码或当前会话身份？（CWE-620）

### 令牌签发与交换

- [ ] 令牌生成是否使用密码学安全随机数，熵 ≥128 位？（ArgoCD CVE-2022-31034：令牌可预测）
- [ ] 认证尝试是否有频率限制 / 锁定策略？（CWE-307；注意 CWE-645 反向 DoS）
- [ ] 默认凭据是否强制首登修改？（CWE-1392/1393）

## A5. 路径与解析绕过认证（CWE-551 / 647 / 424 / 41）

- [ ] 权限判断发生在 URL 归一化**之前**还是之后？先判权限后解码 = 可编码绕过。
- [ ] 测试变形：`../`、`..;/`、URL 双重编码、双斜杠、尾斜杠、大小写、`;jsessionid=` 尾缀是否可绕过过滤器？（TeamCity CVE-2024-27199；Spinnaker 下划线域名 CVE-2026-25534）
- [ ] 代理层与后端的 URL 解析是否一致？（解析差异 = CWE-436 解释冲突）
- [ ] URL 白名单是否依赖有歧义的解析行为（如 Java URL 类对下划线域名的处理）？

## A6. 证明义务（每条候选必须回答）

1. 该端点在入口台账中的认证判定是什么？过滤器链哪一层本应拦住？
2. 伪造/绕过的具体构造是什么（字段、分支、变形路径）？
3. 绕过后的身份是什么级别（匿名→用户 / 用户→admin）？
